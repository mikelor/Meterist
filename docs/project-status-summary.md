## 1. Where the project stands

Meterist is the .NET tool that extracts AI vendor spend from each vendor's API for tracking across client organizations.

**All four v1 vendors are now code-complete and live-verified with real data:**

| Vendor | Status | Notes |
|---|---|---|
| Claude API Platform | ✅ Live-verified | Real dollar cost directly from the API; no seat concept, pure usage pricing |
| ChatGPT Enterprise | ✅ Live-verified | Seat fee + usage/credits. The Daily Usage API (per user, per day) is the source of record; the `COSTS` compliance-log export, which only keeps about 29 days, is a best-effort cross-check |
| Gemini Enterprise | ✅ Live-verified | Per-user activity, aggregate SKU-level dollars via BigQuery billing export |
| Claude Enterprise | ✅ Live-verified for both tenants | Seat fee from the rate configuration plus native per-user dollar usage from the Analytics API. For one tenant, a month's extracted usage matched the invoiced "extra usage units" line exactly, and the seat-fee proration matched the annual contract math |

**Multi-tenancy is proven, not just designed.** Two real tenants (zelleri, ecosync) each have independently configured, DPAPI-encrypted credentials, and both have successfully extracted and persisted isolated data into one shared SQLite database — confirmed via live extraction runs, not just unit tests.

**Other load-bearing pieces now in place:**
- Versioned, per-tenant **rate configuration** (`VendorRateConfig`) with an auto-close-on-renewal policy — setting a new rate automatically closes out the prior open-ended one, so historical spend always resolves against the rate that was actually in effect on that date.
- Credential storage is resilient: a corrupted/stale credential file logs a warning and is treated as empty rather than crashing the whole extraction run.
- **Coverage check:** `audit coverage` lists days with no stored record per tenant and vendor and fails when a seat-priced vendor has a gap, so a missed run is noticed instead of showing up as a quiet stretch in the totals.
- **Scheduled extraction:** a Task Scheduler job runs extraction for every tenant through yesterday, then the coverage check, and writes a dated log.
- **Report generation:** `report generate` builds the Client Spend & Benchmark Report from the stored data, including weekly buckets and annualized projections.
- Raw vendor data is persisted separately from normalized `DailySpendRecord`s, so a normalization bug never loses the underlying pull, and re-extraction is idempotent (upsert by natural key — tenant/vendor/date).

## 2. The ten insights: where each one stands

These are the ten reporting ideas from the original July roadmap, with what exists as of 2026-11-22. Most of them are
sections of the Client Spend & Benchmark Report (`report generate`; each section is described in
`client-report-generation.md`). The backlog and sprint plan are in `product-design-document.md` §7 and the GitHub issues.

| # | Insight | Status | What exists, and what is left |
|---|---|---|---|
| 1 | **Executive TCO rollup**: total spend per tenant, vendor mix, run-rate projection | ✅ Built | The report's headline cards (total tracked spend per tenant, vendor count, average $/day), the vendor ledger and the annualized projection |
| 2 | **Cross-tenant benchmarking**: effective $/seat, usage intensity, compared across clients | 🟡 Partly built | The vendor ledger puts each vendor's spend side by side per tenant, split into seat and usage, and the rate card shows each tenant's seat count and rate. Not built: a computed effective $/seat or usage-intensity ratio as its own figure |
| 3 | **Vendor concentration**: share of spend on one vendor | ✅ Built | The report's concentration section flags any vendor above 70% of a tenant's tracked spend, and says "no vendor above 70%" otherwise |
| 4 | **Cost drivers within a vendor**: by model, workspace or SKU | 🟡 Partly built | "Spend by kind of charge" lists the usage kinds and the not-counted charges (tax, support) where they matter; per-person usage and top consumers show who drives usage, for Claude Enterprise, ChatGPT Enterprise and Claude API Platform (attributed per person or key where the vendor allows). Not built: a split by model or workspace |
| 5 | **Seat efficiency**: over- or under-provisioned seats | ✅ Built | Billed against vendor-reported seats, active users and idle seats in the report, and `audit seats`; it works for every vendor with a roster source: Claude Enterprise and ChatGPT Enterprise, and Gemini Enterprise once its roster is run live (built, not yet run live), not only ChatGPT |
| 6 | **Anomaly and spike detection**: days far above the trailing average | 🔵 Not built, no issue | A stored "unreliable period" flag was decided against (#84), and nothing flags a spike. Revisit if a runaway-usage case shows up |
| 7 | **Day-of-week seasonality** | 🔵 Not built, no issue | Low value until a client asks; the daily data supports it |
| 8 | **Data-quality and coverage disclosure**: what precision each vendor gives, and gaps | ✅ Built | `audit coverage` and the scheduled coverage check; the report's footnotes say which weeks were left out and why, which ChatGPT days came from which source, that tax and support are excluded, and that per-user figures are marked estimated where derived; a vendor with no rate shows a dash with the reason |
| 9 | **Audit and reconciliation**: extracted totals against the vendor's own figures | 🟡 Partly built | Built: the coverage check, per-person usage reconciled to each vendor's aggregate, seat drift, the ChatGPT cross-check of the Daily Usage API against the `COSTS` export, the post-write read-back, and the report-to-report diff that flags a figure that fell. Not built: a command that re-pulls the vendor's own period total and compares it with the stored sum, or an invoice match (deferred, see `vnext-contract-model.md`). Invoices are still reconciled by hand |
| 10 | **Cost projection**: flat, trend-adjusted and latest-week-annualized | ✅ Built | The report's projection section. Partial weeks are left out; the seat part comes from the contract in force on the report's last day; a usage-priced vendor's quiet weeks count as zero. Known limit: the linear Trend figure overstates a series that peaks and then stops (#106) |

The first deliverable proposed in July was a single report combining #1, #2 and #3 (spend, mix and comparative risk).
That report exists and has grown to cover most of the rest. The two largest gaps are a vendor-total reconciliation
command (#9) and the split by model or workspace (#4).

## 3. Open questions worth discussing back in Chat

- **Cadence:** should these insights become a recurring templated report (e.g., generated monthly per client) or a one-off proof-of-value pitch?
- **Priority:** is chargeback detail (#4) or cross-client benchmarking (#2) more valuable to the consulting business model right now — they pull toward different next-build priorities.
- **Interface direction:** this pushes the still-open CLI-vs-dashboard question. A report generator might be the natural next increment either way — worth deciding whether it's a new `report` CLI command, an exported file (CSV/PDF), or the first real reason to start the dashboard.
- **Audit tolerance:** #9 needs a defined "close enough" threshold before it's useful — vendor-reported totals and `DailySpendRecord` sums may legitimately differ by pennies from rounding/proration, so an exact-match check would generate constant false positives. Worth deciding per-vendor tolerance (e.g., dollar or percentage-based) rather than a single global rule, given how differently each vendor's rate/proration logic works today.

## 4. Suggested next steps

1. Prototype #9 (audit/reconciliation) first, or alongside the #1+#2+#3 reporting bundle — it's what turns "live-verified" from a one-time manual spot-check into something repeatable, and de-risks trusting the other insights before they reach a client.
2. Pick one report from the insight list (or the recommended #1+#2+#3 bundle) to prototype next.
3. Decide delivery format — plain-text/Markdown summary from a CLI command, an exported file, or a small HTML dashboard.
4. Decide whether report generation lives inside Meterist itself or as a downstream layer reading from the same SQLite database.
5. Once the #1+#2+#3 bundle and #9 are live, take on #10 (cost projection) — it completes the projection capability, and needs a few more weeks of accumulated daily data to trend against before it's meaningful.
